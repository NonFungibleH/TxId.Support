# The TxID Resolution Object

**Status:** draft for review. Nothing in this document is wired into a live path.
**Why it exists:** TxID's three products (Resolve API, embedded SDK, Console) are
one engine with three consumers. This document defines the thing they all consume.

---

## 1. The problem this solves

Today a diagnosis exists only as **prose generated by a model**. That is fine for a
chat bubble and unusable for anything else:

- A partner's error toast cannot render a paragraph. It needs fields, so it can
  style them, translate them, and decide whether to draw a Retry button.
- A Console list cannot be filtered or counted from prose. "All slippage failures
  this week" requires slippage to be a value in a column, not a word in a sentence.

The concrete test: today nobody can answer *"how many of this project's failures
last week were out-of-gas"*. Not because the data is missing, but because the fact
was never stored as a field. The model read it, wrote a sentence, and the structure
was discarded.

**Half of this already exists.** The EVM decoder returns a typed `cause`
(`out_of_gas | revert_reason | custom_error | panic | unknown_revert`), there is a
typed `PendingDiagnosis`, and Aptos returns typed Move aborts. What does not exist
as data at all is the **resolution half**: whether custody changed, who owns the
next action, whether retrying is appropriate, and what the user should do. Those
live only as English inside a model's answer.

The Resolution Object promotes that half from prose to typed fields.

---

## 2. What the object is, and what it is not

It is a **statement about one attempted on-chain action**: what was tried, what
happened, what it means, and what to do next, with the evidence behind it.

It is **not** a trace, not a receipt, and not a replacement for a block explorer.
It is the interpretation layer above those.

Rendering is the consumer's job:

| Consumer | Renders the object as |
|---|---|
| Resolve API | the object itself, unchanged |
| SDK / embedded agent | an inline message, a status, or conversational prose |
| Console | a searchable row, a timeline, and a case record |

**The rule that keeps this one platform:** the widget's prose is generated *from*
the object. Never the other way round, and never in parallel. If the safety and
responsibility logic is written separately per surface, the surfaces will disagree
with each other inside a month.

---

## 3. Assertion discipline

Every field carries an epistemic status. This is not decoration: an external audit
in August 2026 found that TxID's weakest claims were the ones that outran their
evidence ("verified" where only "sourced" was true). The same discipline applies
here, and it is the reason institutions can accept the output.

| Status | Meaning | Example |
|---|---|---|
| `observed` | Read directly from chain or receipt | gas used, transaction status |
| `derived` | Inferred by applying a known mapping to observed data | `cause` from a revert string |
| `declared` | Asserted by a party, not by us | customer's off-chain workflow event, a hash the user pasted |
| `unknown` | Could not be established | destination state during an indexer outage |

Two fields deserve specific care, because both were phrased as liabilities in the
first strategy draft:

- **Custody.** Never emit "funds are safe" as a bare claim. The object states what
  was *observed*: `custody: "unchanged" | "moved" | "partial" | "unknown"`, plus
  `gas_spent`. "Your funds are safe" is a *rendering* a consumer may choose when
  custody is `unchanged`, and it carries their voice, not an unqualified assertion
  from us.
- **Responsibility.** Never attribute fault to a named third party. The field is
  `next_action_owner`, which says who can act next, not who is to blame.

There is deliberately **no `confidence` percentage.** A number invites a challenge
it cannot survive and tells an operator nothing actionable. The object carries
`basis` instead, which is the same ladder the Case Record already uses.

## 4. The object

```ts
interface Resolution {
  // ---- identity -------------------------------------------------------
  txid_code: string          // "TXID-2003", stable across chains
  cause: CauseSlug           // "OUT_OF_GAS", the machine name
  category: Category         // lifecycle stage where it broke

  // ---- outcome (observed) ---------------------------------------------
  status: Status             // what happened to the attempt
  intent?: Intent            // what the user was trying to do, if the caller said
  intent_met?: boolean       // only meaningful when intent was supplied

  // ---- assessment ------------------------------------------------------
  custody: Custody           // did assets move: observational, never "safe"
  gas_spent: boolean         // was a fee charged for the failed attempt
  next_action_owner: Owner   // who can act next, NOT who is at fault
  retryable: Retryable       // is retrying appropriate, and after what
  recommended_action: ActionCode

  // ---- rendering (the only prose the object carries) -------------------
  summary: string            // one line, safe to show a user
  detail: string             // the fuller explanation
  next_step?: string         // imperative instruction when there is one

  // ---- provenance -------------------------------------------------------
  basis: Basis               // verified | derived | reported | indeterminate
  evidence: EvidenceSource[] // same shape the Case Record already stores
  raw?: string               // the original error text, always preserved
  chain?: string
  hash?: string
  observed_at: string        // ISO timestamp of the read
  chain_state_at?: string    // block or ledger version the answer was true as of
}
```

### Enumerations

```ts
type Category =
  | "SUBMISSION"          // never validly reached the chain
  | "BALANCE"             // insufficient funds or gas
  | "MEMPOOL"             // accepted but not included
  | "APPROVAL"            // permission to move tokens
  | "PROTOCOL_CONDITION"  // a protocol rule rejected it
  | "CONTRACT_DEFECT"     // an invariant broke: a bug, not a user error
  | "SETTLEMENT"          // executed, outcome incomplete or pending
  | "OFFCHAIN_PROCESS"    // waiting on a workflow the chain cannot see
  | "INDETERMINATE"       // not enough evidence to classify

type Status =
  | "not_submitted"          // never reached the network
  | "pending"                // submitted, not yet resolved
  | "failed"                 // executed and failed
  | "succeeded"              // executed and succeeded
  | "succeeded_intent_unmet" // succeeded on chain, user's goal not achieved

type Custody   = "unchanged" | "moved" | "partial" | "unknown"
type Owner     = "user" | "application" | "protocol" | "infrastructure" | "none" | "unknown"
type Retryable = "yes" | "after_change" | "no" | "unknown"
type Basis     = "verified" | "derived" | "reported" | "indeterminate"
```

`status: "succeeded_intent_unmet"` is the field no explorer can produce. A
transaction can succeed technically while the customer's actual goal fails. It
requires the caller to tell us the intent, which is exactly what the SDK and
Partner integrations supply.

## 5. The taxonomy

Codes are grouped by **where in the lifecycle the attempt broke**, because that is
objective. Responsibility is a separate field, because it is a judgement.

| Range | Category | Reading |
|---|---|---|
| 1xxx | SUBMISSION | it never really started |
| 2xxx | BALANCE | there was not enough of something to pay with |
| 3xxx | MEMPOOL | the network would not include it |
| 4xxx | APPROVAL | permission to move the tokens was missing |
| 5xxx | PROTOCOL_CONDITION | the protocol's own rules rejected it |
| 6xxx | CONTRACT_DEFECT | the contract hit a state it did not expect |
| 7xxx | SETTLEMENT | it ran, but the outcome is not complete |
| 8xxx | OFFCHAIN_PROCESS | something off-chain has not finished |
| 9xxx | INDETERMINATE | we will not guess |

The first codes are **mapped from failures TxID already diagnoses**: the 43 entries
in the public error reference, the EVM decoder's typed causes, the pending
diagnosis causes, and the Aptos Move abort maps. See `registry.ts` for the
authoritative list.

Two design rules:

1. **A code is chain-agnostic.** `TXID-2001 INSUFFICIENT_GAS_BALANCE` covers
   Ethereum ETH, Avalanche AVAX, Aptos APT and a failed paymaster sponsorship.
   The chain-specific detail lives in the case fields, not the code.
2. **A code names the condition, never the fix.** Fixes change with protocol
   versions; conditions do not.

## 6. Worked example

A Decibel spot order on Aptos that aborted because the wallet was short on one
side of the pair:

```json
{
  "txid_code": "TXID-2005",
  "cause": "INSUFFICIENT_TOKEN_BALANCE",
  "category": "BALANCE",
  "status": "failed",
  "custody": "unchanged",
  "gas_spent": true,
  "next_action_owner": "user",
  "retryable": "after_change",
  "recommended_action": "ADD_TOKEN_BALANCE",
  "summary": "The order was rejected because the wallet was short on one side of the pair.",
  "detail": "The balance check runs before anything is placed, so nothing was traded and only the network fee was spent.",
  "next_step": "Top up the wallet, or reduce the order size, and retry.",
  "basis": "verified",
  "evidence": [
    { "kind": "transaction", "hash": "0x666ac3...", "chain": "aptos", "origin": "looked_up" },
    { "kind": "contract", "address": "0x50ead2...", "chain": "aptos", "fn": "spot_order_public_api" }
  ],
  "raw": "Move abort in 0x50ead2...::spot_order_public_api: EINSUFFICIENT_PFS_FUNDS(0x1)",
  "chain": "aptos",
  "observed_at": "2026-08-25T09:14:00Z",
  "chain_state_at": "6908400201"
}
```

Note what each product does with the same object:

- **API**: returns it. Team Finance's error screen reads `summary` + `next_step`
  and draws a Retry button because `retryable` is not `"no"`.
- **SDK**: renders `summary` inline; the agent uses `detail` and `evidence` if the
  user asks a follow-up.
- **Console**: a row filterable by `category=BALANCE`, sortable by `basis`, with
  the evidence and raw string on expand, ready to paste into an email reply.

## 7. What this deliberately does not do yet

- **No confidence score.** By design, see section 3.
- **No fault attribution.** `next_action_owner` is about who can act.
- **No off-chain process states in v1** beyond the 8xxx placeholders. Those need a
  partner to supply workflow events; the codes exist so the shape is stable when
  one does.
- **No claim that a diagnosis satisfies a regulatory obligation.** It produces
  better evidence for the customer's own framework. Nothing more.

## 8. Build sequence and blast radius

| Phase | What | Touches the live widget? |
|---|---|---|
| 0 | This spec | No. It is a document. |
| 1 | `lib/resolution/*` pure functions + tests | No. Nothing imports it. |
| 2 | Resolve API route + Console read it | No. Both work server-side from a hash. |
| 3 | Widget renders prose *from* the object | Yes: last, behind a per-project flag, demo project first. |

Phases 0 to 2 do not intersect with the code path any beta tester runs. That is
deliberate: the two new products can be built to completion before the existing
one changes at all.
